## 一、核心架构:三层独立 LLM,绝不混层

不要让一个 LLM 同时做"想剧情" + "演角色" + "写小说"——它会出戏。拆成三层:

```
            ┌──────────────┐
            │   Director   │  仅做编排:本轮在哪 / 谁在场 / 谁发声 / 开场契机
            │  独立 LLM 调用 │  不扮演任何角色,不写对白
            └──────┬───────┘
                   │
       ┌───────────┼───────────┐
       ▼           ▼           ▼
   ┌───────┐   ┌───────┐   ┌───────┐
   │Agent₁ │   │Agent₂ │   │Agent₃ │  每个角色独立 LLM 调用
   │ 凤姐  │   │ 探春  │   │  ...  │  带各自人设 / 声音指纹 / 雷区
   └───┬───┘   └───┬───┘   └───┬───┘  产出 monologue / action / dialogue
       │           │           │
       └───────────┼───────────┘
                   ▼
            ┌──────────────┐
            │   Timeline   │  结构化 JSON 记录,无任何叙事文字
            │ (中间产物)   │  manifest / timeline / usage 三件套落盘
            └──────┬───────┘
                   ▼
            ┌──────────────┐
            │  Composer    │  把 timeline 编织成目标作品语体的小说叙事
            │  独立 LLM 调用 │  保留对白原文,用叙述衔接
            └──────────────┘
```

**为什么必须三层?**(教训出处:Phase A 之前的设计讨论)

- 让 agent 直接吐小说会出戏(它既扮演角色又当作家,两个身份打架)
- 让一个 LLM 同时演 5 个角色会角色串味(声音指纹失效)
- 让 Director 顺便写对白会破坏"声音指纹"约束

## 二、角色档案 Schema(主角与 NPC 共用)

每个角色一份 JSON,字段固定:

```json
{
  "id": "string,英文小写,程序内唯一标识",
  "name": "string,中文名(展示用)",
  "name_pinyin": "string,拼音",
  "identity": "string,1-2 句话,本回身份与处境",
  "personality": "string,1-2 句话,核心性格",
  "relationships": [
    {"type": "亲属 | 主仆 | 朋友 | 情侣 | 敌对 | 同事 | 师徒",
     "description": "1 句话描述这条关系"}
  ],
  "key_events": ["事件 1", "事件 2", ...],
  "voice_fingerprint": {
    "high_freq_words": ["该角色的标志性高频词,4-5 个"],
    "quotes": ["该角色的标志性原话,主角 10 条 / NPC 3-5 条"],
    "speech_style_notes": "string,1 句话总结说话特征"
  },
  "no_go_list": ["绝不会做的事,主角 10 条 / NPC 3-5 条"],
  "source": "string,数据来源备注"
}
```

**关键设计选择**:

- **主角与 NPC 共用 schema**——只是数组长度不同。这样 prompt builder 完全复用,
  不需要分主角/NPC 两套代码路径。(Phase C 教训:NPC 用 schema 子集而非另立结构,
  代码省一半)
- **`high_freq_words`、`quotes`、`speech_style_notes` 三件套**是声音指纹核心
  ——任何作品任何角色都需要这三块,缺一不可
- **`no_go_list` 必须是"绝不会做的事",不是"价值观"**——negative 约束比 positive
  更容易被 LLM 守住

**新作品如何快速生成档案?**

- 主角:从原文里手工抽 voice fingerprint(10 条原话)+ 雷区(10 条)。
  这一步**极不能偷懒**,是整个仿真质量的根基。
- NPC:可以从 GraphRAG 抽出的 `entities[].description` 加一些手工补充快速构造,
  3-5 条就够。(Phase C 教训:NPC 用 5 条原话 + 5 条雷区,质量已足以撑住
  本回戏剧浓度)

## 三、Director Prompt 设计的五条铁律

(出处:Phase B 初版 + Phase C 长程节奏增强)

1. **铁律 1:让不同角色在不同轮次都有戏份**。N 个 agent 中至少 ⌈N×0.7⌉ 个发声过。
2. **铁律 2:反事实偏离要持续放大,不能向原作回收**。这一条对 Director 反复强调。
3. **铁律 3:每轮 speaking_agents 控制在 2-4 人**。太多变群口戏,太少缺张力。
4. **铁律 4:严格输出 JSON,不要 markdown 代码块**。配 `response_format=json_object`
   作双保险,有些模型不支持时降级为普通调用。
5. **铁律 5:10 轮整体节奏分三段**——锚定(R1-3)/ 升级(R4-7)/ 收束(R8-10)。

**Director 必须输出的 JSON schema**:

```json
{
  "location": "本轮场景位置",
  "time_advance": "时间推进描述",
  "present_agents": ["agent_id", ...],
  "speaking_agents": ["agent_id", ...],
  "round_seed": "本轮契机,让发声角色有事可应",
  "narrator_note": "本轮场面与背景旁白"
}
```

**校验函数必备**:`speaking ⊆ present ⊆ all_agent_ids`,空 fallback 取 present 前 2。
单调性校验出现倒序立即告警。

## 四、Agent Prompt 设计的三条核心约束

(出处:Phase A → B 演进)

1. **System prompt 完全展开人设**——身份 / 性格 / 关系 / 高频词 / 原话 10 条 /
   说话特征 / 雷区 10 条全部塞进去。
   - 不要省略雷区清单(看似负面,实际是定义角色边界的关键)。
   - 不要把 monologue 字段对其他 agent 可见(它是私密内心,只有当事 agent 自己知道)。

2. **User prompt 提供本轮上下文**:
   ```
   场景设定 / 关键反事实变量 / 当前位置 · 时间 / 迄今已发生(扁平历史)
   / 本轮场面旁白 / 本轮契机(必须直接对此反应)
   ```

3. **输出严格 JSON**(monologue / action / dialogue),其他 agent 看不到 monologue,
   只看到 action 与 dialogue。

**温度建议**:
- Agent 调用:`temperature = 0.7`(创作类需要温度,但要给戏剧张力)
- Director 调用:`temperature = 0.6`(略稳,要保持编排连贯性)
- Composer 调用:`temperature = 0.65`(中庸,稳但不死板)

## 五、Composer Prompt 设计的九条铁律

(这是踩坑最多的部分,所有铁律都标注教训出处)

1. **目标作品语体**——红楼用章回笔法,武侠用《史记》体,哈利波特用现代英式叙事。
   语体相关的过渡词列表要进 system prompt(如红楼:却说 / 且说 / 话分两头 / 不在话下)。

2. **保留对白原文逐字不改**——agent 的 dialogue 已经过声音指纹约束,Composer 改写
   会破坏声音指纹的整套投资。Composer 只在对白前后加叙述衔接。

3. **整合 narrator_note 进叙事**——Director 写的旁白是高质量场面描写素材,无缝融入。

4. **内心独白(monologue)节制使用**——只挑 3-5 处用"心下暗忖""暗道"等手法点出。
   其余靠动作神态暗示。**不要每个 monologue 都外露**,会啰嗦。

5. **N 段式结构 + 各段字数预算**——Composer 容易在某一段超长某一段过短。
   显式给每段字数(比如 600 / 600 / 800 / 1200 / 800)能让 LLM 自我约束。

6. **目标作品的特有结构标记**——红楼:"话说"开篇 + "且听下回分解"收尾。
   不同作品换不同标记,但**必须有结构开闭符**,否则 LLM 会写不出"完整感"。

7. **【⚠核心】每个 timeline event 只在一个章回出现一次**——LLM 在章节衔接处
   天然倾向 recap 上一段最戏剧的事件,不显式禁止几乎一定会重影。
   - 教训出处:Phase D v1,司棋 R8 整段台词在第三回末和第四回中段被复述
   - 同一 dialogue / action 只能进入一个章回,另一回最多用"且不细表"带过

8. **【⚠核心】戏份少的角色用"叙事 device"补存在感,不要硬给戏**——
   - 红楼:"话分两头""按下不表"
   - 现代小说:视角切换
   - 影视剧本:cross-cut
   - 教训出处:Phase D v1,黛玉/宝钗 中段消失,读者会忘
   - 约束:只点"在场状态",不能加新对白或动作,**单句不超 30 字**

9. **【⚠核心】任何减少文本量的规则,必须配套补偿规则**——
   - 元规律:防御性规则永远成对出现
   - 教训出处:Phase D v2,执行规则 7 削掉 ~150 字,但没补偿,字数跌出区间
   - 4 类合法补偿渠道:
     ① 场景环境描写(意象具象化)
     ② 人物神态(沉吟/垂眸/蹙眉/屏息)
     ③ 转场过渡密度(少顷/须臾/半晌)
     ④ 动作神态暗示内心(不引 monologue)
   - **绝不允许**靠加新对白/独白凑字数(违反铁律 2)

## 六、Prompt 工程的元规律(跨作品普适)

(从 Phase A-E 5 次迭代里沉淀出来的)

1. **prompt 即代码,教训即注释**——把规则添加的"为什么"和"教训出处"内嵌到
   prompt 上方的注释里。**比单独维护一个 design notes 文档更稳**——文档容易腐烂,
   注释和代码同步演进。

2. **正反例对照胜于抽象描述**——
   - 抽象写"要具象、要呼应剧情"——LLM 听不懂
   - 具体写"v1 的'一掌未落风波起,双信入袖暗流深'胜过 v2 的'一波未平一波起'"
     ——LLM 直接学会
   - 教训出处:Phase E v3,这条对照让 Composer 生成了比 v1/v2 都好的 6 句回末诗

3. **防御性规则永远成对出现**——
   - 加"防 X"必须同时加"被 X 削掉的部分用 Y 补偿"
   - 否则规则越多文本越窄,直到撑不起目标体量
   - 教训出处:Phase E v2 → v3

4. **字数硬指标必须显式声明**——
   - 不写"4000 字 ± 200,跌出即失败",LLM 会自由发挥写到 2500 或 6000
   - 校验函数同步落盘,跑完自动算

5. **每条规则都打上版本号 + 出处**——
   - `v3 (Phase E iteration #2)` 这种 tag 让 5 次迭代后还能回溯哪条是哪次加的
   - 任何 prompt 改动都更新版本号 + 加注释说明动机

6. **校验函数与 prompt 同步演进**——
   - prompt 里说"对白要保留",校验里就要算保留率
   - prompt 里说"不要捏造实体",校验里就要查实体是否在源文出现
   - 教训出处:Phase D 校验函数 bug(校验剥光标点对原文带标点,误报 0%),
     说明校验函数和 prompt 一起测、一起改,不能 prompt 改完不验校验

## 七、单作品启动 Checklist

把同一套流水线套到新作品时,按这个清单走:

### 数据层

- [ ] 拿到原作干净文本(避免 OCR'd 文本带来的噪声;若必须 OCR,准备清洗脚本
      参考 `scripts/extract_and_clean.py`)
- [ ] 决定要做的"反事实分支":选一个有戏剧张力的关键场景作为 divergence 锚点
- [ ] 选定 5-7 个核心角色,**手工**整理 5 主角档案(JSON)
      ——每人 10 条声音指纹原话 + 10 条雷区,**这一步不能偷懒**
- [ ] 用 GraphRAG / 直接 LLM 抽出关键章节图谱(参考 `scripts/build_graph.py`)
- [ ] 手工校准图谱:删幻觉实体、补漏抽实体、修关系类型
      (参考 ch74.json 的 manual_edits_summary 字段)
- [ ] 整理 4-7 个 NPC 档案(NPC 档案可以 lite,5 条原话 + 5 条雷区即可)

### 工程层

- [ ] 复制 `scripts/simulate.py` 模板,替换:
  - `ALL_MAIN_AGENTS` / `NPC_AGENTS` 列表
  - `SCENE_DESCRIPTION` / `DIVERGENCE` 文本
  - `DIRECTOR_SYSTEM_PROMPT_C` 中 5 主角的"人物简介"行
  - `COMPOSER_SYSTEM_PROMPT_A` 中目标作品语体相关的过渡词与开闭符
- [ ] `.env` 配置好 LLM API key(DeepSeek 跑一次完整 demo ~¥0.15)
- [ ] 跑 Phase A → B → C → D → E,每步贴输出做验收
- [ ] 进 Phase E 时按"v1 → v2 → v3"循序迭代,每次只加 1-2 条规则,版本号同步更新

### 验收层

- [ ] Phase C 验收:11 个 agent 中至少 8 个发声、至少 3 个不同 location、
      反事实在 R4 后不再被讨论
- [ ] Phase D 验收:字数硬指标内、对白保留率 ≥ 90%、5 段结构完整、
      开闭符正确、无现代词污染
- [ ] D7 盲测验收:5-10 位目标作品资深读者盲读,均分 ≥ 7/10

## 八、成本与性能基线(DeepSeek-chat 实测)

ch74 抄检大观园场景,合计:

| 阶段 | 调用数 | input tokens | output tokens | 成本 |
|---|---|---|---|---|
| Phase A | 2 | 2,176 | 172 | ¥0.003 |
| Phase B | 12 | 17,762 | 1,270 | ¥0.021 |
| Phase C | 43 | 102,852 | 12,485 | ¥0.121 |
| Phase D × 3 iter | 3 | 16,489 | 10,452 | ¥0.038 |
| 图谱抽取 × 2 iter | 2 | 18,562 | 5,229 | ¥0.030 |
| **合计** | **62 calls** | **~158k** | **~30k** | **~¥0.21** |

**关键比例**:
- 单次完整推演(C+D 合计):~¥0.16,~7 分钟串行
- 单次 Composer 调优:~¥0.013,~50 秒
- 整个 demo 从零做到 demo-ready 标准:**~¥0.21,约 30 分钟工程时间**

**MVP 阶段成本预估**:每用户每次完整推演 ~¥0.16-0.30(看模型选择)。
配合 doc 13 定价(38/268 元订阅档),毛利率应该在 50-70% 区间。
但记得:**LLM API 价格会变,记忆文件里的"四项成本控制"必做**(模型分层路由 /
公版图谱跨用户复用 / token 配额翻译层 / 配额耗尽自动降级)。

## 九、常见踩坑清单

### 9.1 数据层踩坑

| 现象 | 根因 | 应对 |
|---|---|---|
| GraphRAG 抽出的实体 30% 是幻觉 | prompt 里给了具体实体清单 | prompt 不要列具体清单,加严格的"只从原文抽取"约束 |
| OCR 文本里"晴雯" → "睛雯"、"贾琏" → "贾旭" | OCR 形近字混淆 | 维护一个**100% 确认**的修正表,宁可漏改不要错改 |
| 章节切分把目录页当成了章节起始 | 目录页有所有章节号 | 用"页内章节头计数 ≥ 2 即视为目录"识别,而非固定页数阈值 |

### 9.2 仿真层踩坑

| 现象 | 根因 | 应对 |
|---|---|---|
| Director 让同两个 agent 独占所有轮次 | 无戏份分布约束 | system prompt 加"N 个 agent 中至少 ⌈N×0.7⌉ 发声过" |
| 反事实在 R4-10 仍被反复讨论(原地踏步) | 无节奏约束 | system prompt 加"R4 后焦点必须移向下游事件" |
| 10 轮全在同一个场景 | 无空间约束 | system prompt 加"至少 3 个不同 location" |
| 配角 NPC 在场不发声 | 仅主角档案完整,NPC 没建 | 给 NPC 也建档案(可 lite 版),进 Director 可选名单 |

### 9.3 前端踩坑(Day 2 增补)

| 现象 | 根因 | 应对 |
|---|---|---|
| 进页面要等很久,且点击任意节点会触发"加载中"再次出现 | Vue `watch` 用了 `{ deep: true }` 监听 force-graph 的数据 prop。force-graph 每帧 mutate `node.x/y/z` 等坐标字段,deep watcher 误判成数据变化,反复重启 simulation,onEngineStop 永远不触发 | watcher 只看 reference 变化,绝不用 deep。需要细颗粒度时用版本号 ref 或 length 浅快照 |
| 1000+ 节点初次加载有 10-20 秒卡顿 | force-graph 默认 `cooldownTicks(Infinity)` + `cooldownTime(15000)`,等 simulation 自然冷却 | 显式 `cooldownTicks(N)` + `cooldownTime(ms)`,小图谱(< 50 节点)用 80/2000,大图谱视压测调整 |
| Halo / 光晕 mesh 让 1000 节点 FPS 减半 | 每个节点都加了独立 halo Mesh,实质 draw call 翻倍 | 冷启动期间 opacity=0,onEngineStop 后 0.4s 渐显;或用 postprocessing UnrealBloom 替代 per-node halo |
| 加了"仿真启动相机推近"动画后,图谱完全拖不动了 | 把 `cameraPosition()` 调用塞在了同时监听 dimMode + participants 的 watcher 里,participants 变化也会触发相机动画,**1.2s 动画期间 OrbitControls 被覆盖**,且每次动画都把 camera 强行拉回 (0,0,z),用户已经做的旋转角度全丢失 | ① 把相机动画拆出独立 watcher,只监听 dimMode 真实变化(prev 对比) ② 沿 camera→target 方向 dolly,保留旋转角度,而非粗暴 setPosition({0,0,z}) ③ cameraPosition 的 lookAt 不要传 undefined,显式传 controls.target |

**通用元教训(适用于 Vue + 任何"会自我 mutate 数据"的库,如 d3-force / vis-network / pixi)**:
**任何会被外部库直接 mutate 内部字段的数据,Vue watcher 绝不能 deep:true**。
应改用 reference 对比、显式版本号 ref、或 length/key 浅层快照。

### 9.4 Composer 层踩坑

| 现象 | 根因 | 应对 |
|---|---|---|
| 司棋台词在第三回末 + 第四回中段被复述 | 无防重复约束 | 加铁律 7(每个 event 只出现一次) |
| 黛玉/宝钗 中段消失,读者会忘 | 戏份少的角色没"在场提示" | 加铁律 8(用"话分两头"等 device 点存在) |
| 加防重复后字数掉到 3688 | 削减规则没配套补偿 | 加铁律 9(4 类补偿渠道明确化) |
| 末段回末诗变成"一波未平一波起"空泛对仗 | 未给质量定向 | 在铁律里直接给正反例对照 |
